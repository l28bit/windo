# WINDO CI Architecture

## Purpose

WINDO's CI system is a safety system, not a dashboard decoration. A green signal must correspond to a proven engineering property. A red signal must correspond to a failed property or an intentionally detected policy violation. Workflow-definition noise, stale branch races, host-dependent generated bytes, and ambiguous side-effect steps are CI-platform defects.

This document defines the operating contract for `.github/workflows`.

## Steady-state automatic path

An ordinary pull request into `jonex/windo-production-ready` should be understandable as three layers:

1. **WINDO Workflow Definition Guard** — prove that the CI platform itself is valid and trustworthy.
2. **WINDO Fast Gate** — return inexpensive source feedback quickly.
3. **WINDO Deep Certification** — run the expensive Windows/runtime/trust/reproducibility contract and expose one stable aggregate result.

Everything else is manual diagnostics, control-plane observability, release publication, or post-publication canarying. A workflow that does not fit one of those roles should not exist merely because another YAML file is easy to create.

## Core principles

1. **Validation is read-only.** Ordinary CI never mutates the branch or commit it validates.
2. **Writers are exceptional.** Only Release Factory and Engineer Journal Capture are approved steady-state writers. Any new writer is a security architecture change.
3. **Laboratories do not repair production.** Repair Laboratory, Flake Hunter, and Regression Bisect produce evidence. Materializing a code change is a separate reviewable engineering action.
4. **Red means evidence.** Zero-job parser failures, stale non-fast-forward races, expected unsigned-candidate states, and optional side-effect failures must not masquerade as product-test failures.
5. **Green side effects are observable.** A workflow that creates durable state must report the actual resulting branch/release object rather than merely report that a command was attempted.
6. **External Actions are immutable and current.** Every external `uses:` reference is pinned to a full 40-character SHA, and deprecated Node-20 action pins are forbidden.
7. **Workflow definitions are code.** actionlint plus WINDO policy validates the workflow estate before it enters the clean lane.
8. **Private signing remains private.** Hosted Actions may prove a PreSign candidate but never receive the private key and never manufacture `checksums/installer.sha256.sig`.
9. **Generated bytes are canonical.** Release/generated text is LF-canonical independent of checkout OS. Files whose bytes participate in reproducibility are pinned by `.gitattributes`.
10. **Failures remain engineering memory.** Failed hypotheses and meaningful failed experiments are preserved in the Engineer Journal rather than rewritten into a cleaner story.
11. **Required checks are stable contracts.** Branch protection should depend on small stable aggregate check names, not individual matrix leaves.
12. **Newest source wins for temporary materializers.** A stale repair run must cancel or fail rather than overwrite newer repository state.

## Workflow inventory

### Automatic required-check candidates

#### `windo-workflow-guard.yml` — WINDO Workflow Definition Guard

Runs actionlint and `tools/Test-WindoWorkflowPolicy.ps1`.

It proves:

- workflow YAML / expression / embedded shell validity;
- immutable 40-character external Action pins;
- rejection of known deprecated Node-20 Action pins;
- explicit write-capability allow-list;
- no `pull-requests: write` workflow permission;
- no direct pushes into authoritative development/release branches;
- no force pushes;
- manual-only trigger policy for engineering laboratories/capture workflows.

#### `validate.yml` — WINDO Fast Gate

One Windows Server 2022 job provides fast PR feedback:

- Windows PowerShell 5.1 parser compatibility for critical PowerShell sources;
- reserved automatic-variable safety;
- lightweight source logic tests;
- Engineer Journal contract, including modular entry validation.

The reusable journal policy lives in `tools/Test-WindoJournalContract.ps1`. Journal entry construction lives in `tools/New-WindoJournalEntry.ps1`. Important behavior therefore exists as repository code rather than YAML-only shell fragments.

#### `windo-ci.yml` — WINDO Deep Certification

Deep Certification owns expensive hosted evidence:

- source/trust contract;
- Windows Server 2022 and 2025 compatibility;
- Windows PowerShell 5.1 and PowerShell 7 runtime lanes;
- generated-artifact reproducibility;
- fail-closed negative trust paths;
- retained forensic artifacts for failing compatibility lanes;
- one stable aggregate check: `WINDO Deep Certification green`.

Issue-specific compatibility waivers are temporary debt. Once the corresponding repaired runtime is merged and signed, the general Deep Certification contract must absorb the strict proof and remove the waiver.

### Manual engineering instruments

These workflows are intentionally `workflow_dispatch` only and are not ordinary PR status noise.

#### `windo-repair-lab.yml` — WINDO Repair Laboratory

Read-only. It can:

- diagnose PS5.1/DPAPI behavior on Server 2022 and 2025;
- regenerate derived artifacts in a disposable checkout and retain the exact patch/status as evidence;
- run PreSign validation against that disposable candidate;
- verify release signature/snapshot/source-hash trust evidence.

It cannot commit, push, open a PR, sign, or publish.

#### `windo-flake-hunter.yml` — WINDO Flake Hunter

Repeatedly runs a selected probe in fresh PowerShell processes across PS5.1/PS7 and Server 2022/2025. It classifies results as not reproduced, deterministic failure, or flaky/stateful and retains every run's evidence.

#### `windo-regression-bisect.yml` — WINDO Regression Bisect

Uses a known-good ancestor, known-bad ref, stable probe, PowerShell host, and Windows generation to locate the first bad candidate commit. A bisection candidate is evidence, not automatic proof of root cause.

### Narrow writer

#### `windo-journal-entry.yml` — WINDO Engineer Journal Capture

Manual-only and `contents: write` only.

It calls `tools/New-WindoJournalEntry.ps1`, creates one structured file under `docs/engineer-journal/`, validates journal structure, and pushes only an isolated `journal/entry-<run>` branch. It does not request `pull-requests: write` and does not claim to create a PR.

### Observability / control plane

#### `windo-failure-triage.yml` — WINDO Failure Triage

Read-only listener/dispatcher that gathers failed jobs, failed logs, runner evidence, and existing artifacts, classifies known failure families, and produces a journal-ready incident candidate.

While `Exodus` remains the repository default branch, GitHub's `workflow_run` event constraint requires a thin listener definition on the default branch. Its workflow-name subscription must be kept aligned with the authoritative names above. If the repository default branch moves to production-ready, the duplicate control-plane definition should be retired.

### Release and post-release health

#### `windo-release.yml` — WINDO Release Factory

Manual-only. Certification runs read-only against `jonex/windo-production-ready`. Only the explicit publish job receives `contents: write`, and it publishes the exact commit emitted by certification. Hosted Actions never receive the private signing key.

#### `windo-public-canary.yml` — WINDO Published Release Canary

Scheduled plus manual. It downloads the exact public-facing `WINDO-Install-Latest.ps1`, parses it under PS7 and PS5.1, compares it to the canonical production bootstrap, and records the public asset hash.

## Retired workflow orchestration

The following historical recovery/validation workflows were removed after equivalent/current coverage existed elsewhere:

- `prometheus-repair-sync.yml`;
- `prometheus-stage-repair.yml`;
- `prometheus-validation.yml`;
- `windo-journal-guard.yml`.

The underlying validation/generation scripts were not deleted merely because old orchestration was retired. Current workflows still use the canonical repository tooling where appropriate.

## Permission model

The steady-state workflow writer allow-list is intentionally tiny:

- `windo-journal-entry.yml` — isolated journal branch only;
- `windo-release.yml` — explicit release publication job only.

Repair Laboratory is read-only. Failure Triage is read-only. Fast Gate, Deep Certification, Definition Guard, Flake Hunter, Regression Bisect, and Public Canary are read-only.

`pull-requests: write` is forbidden by workflow policy. When a workflow materializes a branch, PR creation belongs to an authorized external/user control plane rather than being disguised as a successful Actions side effect.

## Failure semantics

### Product / runtime failure

Examples:

- parser failure in shipping PowerShell;
- reserved-variable violation;
- generated artifact drift;
- DPAPI shipping-helper round-trip failure;
- logic failure;
- release hash mismatch outside an intentional candidate-generation stage.

These are red.

### Trust / policy failure

Examples:

- mutable external Action reference;
- deprecated Action runtime pin;
- invalid workflow syntax/expression;
- undeclared write authority;
- validation workflow attempts to push source state;
- private-signing boundary violation.

These are red.

### Expected PreSign state

A refreshed unsigned checksum manifest with an intentionally stale private signature is valid only inside the explicit PreSign stage. PreSign must still prove source hashes, generated artifact integrity, parser/logic gates, and trust root.

Full release validation must fail until the refreshed private signature exists.

This distinction is currently proven by Issue #8: the strict hosted runtime/reproducibility/PreSign lane is green, while the normal signed source contract stops exactly at `Verify signed release manifest`. That is the desired safety boundary, not a runtime regression.

## Issue #8 lessons incorporated into the platform

Issue #8 exposed several CI-platform properties that are now general WINDO rules:

1. A repair workflow must validate an immutable source SHA rather than mutate the branch being tested.
2. Concurrent materializers use latest-source-wins semantics rather than racing pushes.
3. Generated release text is LF-canonical even when generation runs on Windows.
4. `.gitattributes` includes generated payloads whose checkout EOL would otherwise break reproducibility.
5. Large generated PowerShell structures are synchronized by AST/structure, not fragile host-sensitive regexes.
6. Regeneration must be idempotent; an already-canonical artifact is success, not an error.
7. A volatile timestamp in a tracked generated report is diagnostic churn and should not be treated as release-byte drift.
8. Runtime certification exercises the actual shipping helper and a real DPAPI round-trip rather than only a fixture that approximates the helper.
9. Hosted PreSign success never implies private signing is complete.

The dedicated Issue #8 workflows are temporary migration/certification machinery. Their durable proofs should be absorbed into Deep Certification before the issue-specific workflows are retired.

## Action runtime policy

The workflow estate is standardized on verified Node-24-native releases:

- `actions/checkout` v7.0.1 — `3d3c42e5aac5ba805825da76410c181273ba90b1`;
- `actions/upload-artifact` v7.0.1 — `043fb46d1a93c77aae656e7c1c64a875d1fc6a0a`.

The old Node-20 pins are explicitly rejected by `Test-WindoWorkflowPolicy.ps1`, so runtime regression cannot silently re-enter the workflow estate.

## Branch protection target

`jonex/windo-production-ready` is the authoritative release lineage but repository-side protection is tracked separately because CI cannot enforce server-side branch governance by itself.

Target policy:

- require pull requests;
- prevent force pushes and deletion;
- restrict direct pushes;
- require branch to be current before merge where practical;
- require stable aggregate checks rather than matrix leaves;
- require `WINDO Workflow Definition Guard`;
- require `WINDO Fast Gate`;
- require `WINDO Deep Certification green` once its signed-candidate semantics are finalized.

See issue #10.

## Hosted versus privileged certification

Hosted Actions prove source, parser, logic, trust, reproducibility, non-interactive runtime behavior, and signed/pre-sign release contracts. They do not honestly prove the complete interactive elevated user experience.

Before public release, a privileged disposable Windows lane must prove against the exact signed candidate:

- clean installation;
- real UAC/elevation behavior;
- argument and quoting fidelity;
- stdout/stderr streaming;
- exit-code propagation;
- Ctrl+C/cancellation and process-tree cleanup;
- encrypted audit log creation/integrity behavior;
- self-repair behavior;
- fail-closed corruption/trust behavior;
- uninstall/cleanup;
- PS5.1 and PS7 where supported;
- teardown without persisted credentials or signing material.

See issue #11.

## Current design test

A proposed new workflow should answer all of these questions before it is accepted:

1. Which unique invariant or operational question does it own?
2. Why can that invariant not live in Fast Gate, Deep Certification, or an existing manual laboratory?
3. Is it automatic or manual for a concrete reason?
4. What is the minimum permission it needs?
5. What durable state can it create, if any?
6. How is that side effect verified?
7. What is its stable success/failure meaning?
8. What existing workflow can be removed or simplified because this one exists?

If those answers are weak, the workflow should probably not be added.
